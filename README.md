#AIOps智能运维实战精品班-韩先超、崔皓老师

获课：itazs.fun/21520/AIOps智能运维实战精品班-韩先超、崔皓老师

运维工程师对告警的疲惫是真实的。腾讯音乐分享过一个场景：十年前每人每月处理约三千个电话告警，折合每天一百多个，几乎每十分钟一次，工程师长期处于“一手拿手机、一手握鼠标”的救火状态。传统阈值告警在微服务和云原生架构下彻底失效——固定阈值缺乏泛化能力，面对异构数据流频繁引发告警风暴，平均恢复时间被无限拉长。AIOps 要解决的核心矛盾不是“告警不够准”，而是让运维决策从“凭经验猜”转向“按证据判”。

先看清落地起点：数据管道比模型重要。一套可运行的 AIOps 系统，最贵的从来不是算法，是“接数据”的那层管道。有团队复盘生产级平台时直言，数据采集与归一化占了整个项目一半以上的工程量，却最不容易被看见。Prometheus 管指标、ELK 管日志、SkyWalking 管链路，但真正让根因分析成立的是 CMDB 和发布系统的接入——离了变更记录，根因分析只能瞎猜。一个具体的事故复盘印证了这一点：配置发布将数据库连接池上限从 50 调到 10，引发连接排队，系统在 4 分 12 秒内完成发现到恢复，人工只点击了两次操作：确认根因、点击回滚。让这个速度成为可能的，不是模型多聪明，是变更记录和监控指标在同一上下文里可被关联检索。

异常检测的工程选择，比追求“先进算法”更务实。复杂深度学习在运维场景中并不总是优于统计学方法。腾讯云开发者社区给出的方案是用 EWMA（指数加权移动平均）对趋势做平滑，结合动态标准差计算自适应阈值，替代固定的“CPU > 90% 告警”规则。这套方法在测试环境中运行超过六个月，告警准确率提升 40%。关键判断在于：运维数据的信噪比决定了简单统计方法往往比深度模型更鲁棒，因为业务波峰波谷本身就是正常的“异常”，固定阈值会把大促流量误判为故障，而自适应基线不会。

自愈执行层的分寸感，是生产环境与演示环境的真正分界线。检测到异常就自动重启 Pod 或删节点，在演示里很酷，在生产里很危险。被验证过的做法是“先验证后执行”：自愈 Operator 在触发动作前，先检查目标服务的副本数、当前流量、依赖状态，确认操作不会引发雪崩后再执行，且必须包含 Dry-Run 和回滚机制。有团队为自愈接口配置了分级权限，核心生产集群的自愈动作需要人工二次确认后才执行。宁可漏报，不可误杀，这条纪律比任何算法优化都优先。

从今天开始，如果你准备在团队里落地 AIOps，先别急着选平台或调模型。做一件更基础的事：把你当前最高频的十类告警调出来，逐条标注“触发后值班人员实际做了什么、需要打开几个系统、耗时多少”。如果超过一半的操作是“打开仪表盘看看、然后判断不用管”，你的当务之急不是上根因分析，是把告警规则和可观测数据先打通。AIOps 的起点从来不是算法，是你对自己运维链路里每一个断点的真实认知。
